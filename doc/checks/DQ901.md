# DQ901 statement-key

**Family:** statements, integrity and identities (DQ90x) · **Severity:** error ·
**Applies to:** statements · **Deterministic** (`p_error` = 1)

## What it reports

A version of a statement that cannot be told apart from another, or whose place
on the knowledge timeline cannot be right ([statements.md](../statements.md)). It
reads every version of every period. A period is a statement, a period type and a
fiscal date, and a version is one of its rows.

| Problem | Reported on |
|---|---|
| Two rows for one version: the same statement, period type, fiscal date and `version_no` | the version |
| A `known_from` before the fiscal date: known before the period ended | the version |
| A `filed` version whose `known_from` is not its `filing_date`, or that has no filing date | the version |
| Versions that do not chain | the period |

A version's problems are one report, and a period's chain is another. A row
judged twice is judged once.

**The chain.** A period's versions are ordered by `known_from`, then
`version_no`, as fafnir orders them (its ADR 0018). Each version's `known_to`
must be the next version's `known_from`, and only the last may be open (no
`known_to`). So the chain breaks when:

- a version is closed before the next is known (a gap);
- a version is closed after the next is known (an overlap);
- a version before the last is open: two are open, or an open one is not the last;
- the last version is closed, so that none is in force.

A period with one version chains when that version is open. Two rows of one version
are judged once in the chain, so a duplicate is reported once, as a duplicate.

The chain's suggested action (`set_known_to`) names each version to close and the
day to close it on, or the version to reopen. Its fields map each version (`v1`)
to that day, or to an empty string for a version to reopen.

```
AAA  2010-03-31 Q1 FY2010 income  DQ901 error  statement-key  versions do not chain: v1 is known to 2010-09-01 and v2 from 2010-10-01: a gap  (line 2)
AAA  2010-06-30 Q2 FY2010 income v1  DQ901 error  statement-key  2 rows (lines 4, 5)  (line 4)
AAA  2010-09-30 Q3 FY2010 balance_sheet v1  DQ901 error  statement-key  known from 2010-09-15, before the period ends  (line 9)
AAA  2010-12-31 FY2010 cash_flow v1  DQ901 error  statement-key  filed on 2011-02-20, but known from 2011-02-25  (line 12)
```

**Keys.** A version's report has the version's `record_key`, and a chain's report
has the period's, without `version_no` ([output.md](../output.md)). Its detail lists
the versions as `v1 2010-05-01..2010-09-01, v2 2010-10-01..open`. `--since` keeps a
chain's report while any of its versions was known or loaded on or after the date.

**fafnir.** DQ901 succeeds `fundamentals_version_chain`, which reports the same
periods with the same `record_key`. Its other problems are ones fafnir's
constraints make unstorable: dorq is vendor-neutral, and checks them anyway.

## Fix

Re-export from the source of truth: a duplicate or a broken chain means a write
went around the loader. To repair a chain, set each `known_to` to the next
version's `known_from`, and reopen the last version. A `known_from` before the
period's end, or apart from the filing date, is a knowledge date taken from the
wrong field: take it from the filing.
